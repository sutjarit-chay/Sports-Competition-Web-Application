# คู่แข่งขันไม่ปรากฏในหน้าบันทึกผล

ตรวจวันที่ 16 พฤศจิกายน 2569: โปรแกรมมีผัง 98 คู่ แต่ matches มีเพียง 6 แถว และยังไม่มี referee_id ทั้ง 6 แถว หน้าบันทึกผลเดิมใช้ matches เท่านั้น จึงแสดงว่างเมื่อเลือกรายการที่มีแต่ผัง กรรมการยังถูกจำกัดรายการตามการมอบหมายทั้งที่ UI และ RLS

## การแก้ไข

- แสดงคู่ในผังที่ยังไม่เปิดใช้งานบนหน้าบันทึกผล ผ่าน MatchResultProgram
- ผู้ดูแลกำหนดเวลาแข่งขันจริง สนาม และ UUID กรรมการได้จากหน้านี้ ใช้เส้นทาง schedule เดิมพร้อม revision guard โดยอนุญาตวันเวลาซ้ำตามคำสั่งผู้จัดวันที่ 16 พฤศจิกายน 2569
- คู่ที่เปิดใช้งานแล้วไม่ต้องมอบหมายกรรมการเพื่อเปิดกรอกคะแนน
- กรรมการอ่านรายการผ่าน API ที่ตรวจ role ปัจจุบันแล้วเห็นทุกรายการ ไม่จำกัดตามผู้รับมอบหมาย
- คู่ที่ยังไม่ทราบผู้ผ่านเข้ารอบต้องยืนยันทีมในหน้าจัดการรายการก่อน ไม่สร้างโรงเรียนหรือผลสมมติ
- เปตองที่รอจับสลากและกรีฑาที่รอเปิดฮีตยังต้องจัดเตรียมรายการจริงก่อน ระบบไม่สร้างคู่/เวลาสมมติ

## การใช้งาน

ผู้ดูแลเลือกกีฬาที่หน้าบันทึกผล กำหนดวันเวลาและสนามในส่วนโปรแกรมรอเปิดบันทึกผล ใส่ UUID ผู้รับผิดชอบได้ตามต้องการ (ไม่บังคับ) แล้วกดบันทึกเวลา เมื่อระบบสร้างคู่จริงแล้ว แบบฟอร์มคะแนนจะปรากฏ กรรมการกดโหลดข้อมูลใหม่หลังเปิดคู่

ไม่แก้ schema, constraint, RLS หรือข้อมูลจริงระหว่างตรวจสอบ ไม่มีการมอบหมายกรรมการแบบเหมารวม

## ตรวจสอบ

Regression tests ใน tests/match-result-program.test.ts: แสดงชื่อโรงเรียนและเครื่องมือตั้งค่าคู่ที่ยังไม่ materialize, กรรมการอ่านอย่างเดียว, คู่พร้อมแล้วไม่ซ้ำ, รายการว่าง, ไม่มีคู่มอบหมาย และคู่เดิมที่ยังไม่มอบหมาย

## การกำหนดเวลาซ้ำ

อนุญาตให้หลายคู่ใช้วันเวลาเดียวกันได้ ทั้งภายในรายการเดียวกันและข้ามรายการ แม้ใช้สนามเดียวกันหรือมีโรงเรียนเดียวกัน ใช้กับการสร้างคู่พร้อมแข่งขัน การจัดเวลา การจัดสาย/เลื่อนรอบ และการแก้โปรแกรมผ่าน API บันทึกผลด้วย

ยังตรวจรูปแบบวันเวลา สนาม ทีมแข่งกับตัวเอง สิทธิ์กรรมการ revision และห้ามแก้โปรแกรมคู่ที่ยืนยันผลแล้ว ไม่เปลี่ยนข้อมูลใน Supabase และไม่แก้ schema, constraint หรือ RLS

## สิทธิ์กรรมการร่วมกัน (16 พฤศจิกายน 2569)

กรรมการที่มี role referee หรือ recorder ใน profiles บันทึกคะแนนได้ทุกคู่และทุกฮีตกรีฑาที่เปิดแล้ว โดยไม่ตรวจ referee_id เป็นเงื่อนไขสิทธิ์ การมอบหมายยังใช้ระบุผู้รับผิดชอบ แต่ไม่จำกัดการบันทึกผล

- GET /api/result-workspace ตรวจ token และอ่าน role จาก profiles ทุกครั้ง อนุญาตเฉพาะ admin/referee/recorder แล้วอ่านข้อมูลผ่าน service client ฝั่งเซิร์ฟเวอร์ ไม่มีคีย์ใน response และใช้ Cache-Control: no-store
- หน้ากรรมการโหลดข้อมูลผ่าน endpoint นี้ เพราะ RLS เดิมยังจำกัดการอ่านตรงตามผู้รับมอบหมาย ไม่แก้ RLS/constraint/schema
- ไม่กรองรายการ คู่แข่งขัน รายงาน หรือฮีตกรีฑาตาม referee_id ในหน้ากรรมการอีก
- API ผลกีฬาทีม คะแนนรายเซต กรีฑา และการเลื่อนผู้ชนะ ไม่จำกัดตามผู้รับมอบหมาย
- กรรมการยังเปลี่ยนทีม ตาราง สนาม และการมอบหมายไม่ได้ ยังคงตรวจ revision, คะแนน, ผู้ชนะคัดออก และนักกีฬากับรายการให้ตรงกัน การสร้างรอบชิงกรีฑายังต้องมีผล OK จากฮีต
- คู่ที่มีเฉพาะผังยังต้องเปิดใช้งานและระบุวันเวลา/สนามโดยผู้ดูแลก่อน ไม่สร้างเวลาหรือผลจริงระหว่างแก้โค้ด
- บัญชีผู้ชม โรงเรียน และบัญชีที่ยังไม่ได้รับอนุมัติไม่มีสิทธิ์ endpoint นี้

Node regression tests ครอบคลุมอ่านข้อมูลข้ามผู้รับผิดชอบ การปฏิเสธบทบาทอื่น บันทึกคู่ที่ไม่มอบหมาย/มอบหมายคนอื่น คะแนนรายเซต กรีฑา และการเลื่อนผู้ชนะ ส่วน browser fixture ปรับให้ทดสอบโต๊ะกรรมการร่วมกันโดยไม่เชื่อมฐานข้อมูลจริง

## แก้ตัวตรวจเวลาซ้อนที่หน้าจอ (16 พฤศจิกายน 2569)

พบตัวบล็อกที่เหลือในฟังก์ชัน save ของ app/page.tsx ซึ่งแจ้ง “เวลานี้มีโรงเรียนแข่งขันซ้อนหรือสนามถูกใช้งานในรายการอื่นแล้ว” ก่อนส่ง API แม้ฝั่งเซิร์ฟเวอร์อนุญาตเวลาเดียวกันแล้ว ลบเฉพาะตัวตรวจนี้และ import ที่ไม่ใช้งาน ยังคงตรวจทีมที่ยังไม่ทราบผู้ผ่านเข้ารอบและผลเสมอในรอบคัดออก

Browser regression ใช้สองคู่โรงเรียนเดียวกัน สนามเดียวกัน เวลาเดียวกัน และบันทึกคู่ที่ไม่ได้มอบหมาย ผ่านทั้ง referee และ recorder จำลองข้อผิดพลาดเดิมได้ก่อนแก้ ไม่มีการส่งผลทดสอบไป Supabase จริง

## เมนูกรรมการเพิ่มเติม

ตามคำสั่งผู้จัด เปิดเมนูตารางคะแนน (5) และจัดการรายการแข่งขัน (8) ให้ referee/recorder รวมถึงสิทธิ์ create/update/policy/draw/schedule/advance ใน API จัดการแข่งขันผ่านการตรวจ role จาก profiles ฝั่งเซิร์ฟเวอร์ การแก้ทีม/เวลาใช้หน้าจัดการโดยตรง ส่วน API บันทึกผลยังแก้เฉพาะคะแนน ไม่เปิดสิทธิ์จัดการบัญชี โรงเรียน หรือการล้างการแข่งขัน ไม่มีการเปลี่ยน RLS หรือ schema

# บัญชีโรงเรียนและกรรมการที่รออนุมัติ

ปรับวันที่ 2026-11-06 ตามข้อกำหนด: ผู้ดูแลใช้อีเมล โรงเรียน/กรรมการใช้ username/password และต้องรอผู้ดูแลอนุมัติ โดยรักษาข้อมูลเดิม โหมดสาธิต และไม่แก้ schema, constraint หรือ RLS

## วิธีใช้งาน

1. เปิด `/school-registration` เลือกโรงเรียนหรือกรรมการ กรอกรายละเอียด ชื่อบัญชี และรหัสผ่านใหม่ 10–128 ตัวอักษร ไม่ต้องกรอกหรือยืนยันอีเมล
2. ตรวจข้อมูลแล้วกดส่งคำขอ สมัครไม่ได้รับบทบาททันที หน้าเข้าสู่ระบบอยู่ที่ `/?account=1`
3. ผู้ดูแลเลือกวิธีเข้าสู่ระบบด้วยอีเมล บัญชีอื่นใช้ชื่อบัญชี ผู้สมัครที่รอหรือไม่ได้รับอนุมัติเห็นสถานะ/เหตุผล และยังเป็นผู้ชม
4. ผู้ดูแลโหลดรายการคำขอแล้วตรวจและยืนยันอนุมัติ โรงเรียนได้รับ `school_admin` พร้อมโรงเรียน ส่วนกรรมการใช้บทบาท `referee` ที่ constraint ของระบบจริงรองรับ แสดงชื่อสิทธิ์ว่า “กรรมการ”
5. ผู้สมัครกดโหลดข้อมูลใหม่หรือเข้าสู่ระบบอีกครั้งหลังอนุมัติ จึงเห็นหน้าตามสิทธิ์จริงจาก `profiles`

## ข้อมูลและสิทธิ์

ใช้ [Supabase Auth](https://supabase.com/docs/guides/auth/users) เดิม บัญชีใหม่มี email alias ภายใน `accounts.sports-competition.invalid`; ผู้ใช้ไม่ต้องมีอีเมลจริงและไม่เห็นช่องอีเมลในแบบสมัคร รหัสผ่านส่งให้ Auth เท่านั้น ไม่เก็บใน metadata, localStorage หรือคำขอ

ประเภทบัญชีและรายละเอียดคำขอเก็บใน Auth `app_metadata.registration` ซึ่งเขียนได้จาก backend เท่านั้น ไม่ใช้ `user_metadata` หรือค่าที่ client ส่งมาเป็นหลักฐานว่าบัญชีอนุมัติแล้ว บทบาทที่ทำงานจริงมาจาก `profiles` เสมอ Secret key อยู่เฉพาะ server ไม่ส่งให้ browser

ทั้งสองประเภทใช้ตาราง `school_registration_requests` เดิมเป็นทะเบียนคำขอ รหัสผู้สมัคร/username ใช้ตาม JWT เจ้าของ คำขอกรรมการใช้ `school_name` เป็นข้อความระบุกรรมการ ไม่สร้างโรงเรียนจากข้อความนั้น ประเภทที่เชื่อถือได้อยู่ใน server-managed Auth metadata

การอนุมัติโรงเรียนใช้ RPC `review_school_registration` เดิมที่สร้างโรงเรียนและ profile ใน transaction เดียว API ตรวจว่าเป้าหมายไม่ใช่คำขอกรรมการก่อนเรียก RPC

การตรวจกรรมการใช้ conditional UPDATE รับคำขอจากสถานะ pending เพียงครั้งเดียว ก่อนสร้าง profile หรือเขียนสถานะ Auth จึงไม่รับทั้งอนุมัติและไม่อนุมัติพร้อมกัน ระหว่างดำเนินการ ใช้สถานะ approved พร้อม JSON marker ภายใน review_note เป็นบันทึกงานที่ยังไม่จบ; หน้าเว็บยังแสดงตามสถานะคำขอจริงและ profile เมื่อเสร็จจะเขียนสถานะสุดท้ายและหมายเหตุปกติ ไม่เปลี่ยน constraint/status values เดิม

เลือกสถานะชั่วคราวนี้เพื่อไม่ให้ RPC ส่งคำขอใหม่เดิมของผู้สมัครแก้คำขอที่กำลังดำเนินการ ซึ่ง RPC นั้นอนุญาตเฉพาะแถว rejected ค่าชั่วคราวไม่ใช่หลักฐานว่าบัญชีได้รับสิทธิ์ และไม่ถูกนำไปแทนการตรวจ profiles

หากสร้าง profile ไม่สำเร็จ จะคืนคำขอเป็น pending โดยมีเงื่อนไขว่าเป็นงานเดิม หากสิทธิ์สร้างแล้วแต่ขั้นตอน metadata/finalization สะดุด จะไม่ลบสิทธิ์หรือข้อมูลอื่นเพื่อแก้ปัญหา ผู้ดูแลโหลดคำขออีกครั้งและดำเนินการต่อตามคำตัดสินเดิมหลัง 2 นาที การรับงานต่อใช้ timestamp CAS และคงคำตัดสิน เหตุผล และผู้ตรวจเดิม การเปลี่ยนคำตัดสินใหม่ไม่ใช่ฟังก์ชันของการลองซ้ำนี้

## บัญชีเดิม

บัญชีโรงเรียน/กรรมการที่ได้รับสิทธิ์แล้วและยังใช้อีเมล ใช้ชื่อส่วนหน้า @ และรหัสผ่านเดิมได้ Backend แปลงชื่อกลับเป็น email ภายในโดยไม่แก้ Auth user/profile/ทะเบียน รหัสผ่านเดิมที่สั้นกว่า 10 ตัวอักษรยังเข้าสู่ระบบได้ กฎขั้นต่ำ 10 ใช้เฉพาะสมัครใหม่

ไม่เดาเลือกบัญชีเมื่อชื่อซ้ำ ผู้ดูแลสามารถกำหนด `app_metadata.login_username` ให้เป็นชื่อที่ผ่านรูปแบบเดียวกันและไม่ซ้ำ บัญชี admin ยังต้องใช้หน้าอีเมล บัญชีเดิมและชื่อที่สงวนไว้จะไม่ถูกสมัครใหม่มาทับ

ชื่อบัญชีใหม่ยาว 3–32 ตัวอักษร ใช้ a–z, 0–9, จุด ขีดล่าง ขีดกลาง โดยขึ้นต้น/ลงท้ายด้วยตัวอักษรหรือตัวเลข ไม่แยกตัวพิมพ์เล็ก–ใหญ่ การค้นชื่อผ่าน Auth admin API แบ่งหน้า จึงเหมาะกับขนาดงานโรงเรียนนี้; หากเพิ่มผู้ใช้จำนวนมากควรพิจารณาทะเบียน username ที่มีดัชนีแยกในงานฐานข้อมูลที่ได้รับอนุญาตภายหลัง

## ก่อนใช้บนระบบจริง

- ตั้ง `NEXT_PUBLIC_SUPABASE_URL` และ public key พร้อม `SUPABASE_SERVICE_ROLE_KEY` เฉพาะ backend environment ไม่ใช้ secret กับ prefix NEXT_PUBLIC และไม่ commit ไฟล์ env
- ใช้ schema normalized เดิมที่มีตารางคำขอและ RPC ตาม migration 20261105 ที่ตรวจติดตั้งไว้แล้ว การเปลี่ยนนี้ไม่รัน SQL หรือ migration
- Service role ต้องมีสิทธิ์ Auth admin และ DML บนตารางคำขอ/ profiles สำหรับงานที่ admin อนุมัติ ถ้าข้อกำหนดเดิมไม่รับ referee หรือ DML ถูกปฏิเสธ ระบบแจ้งข้อผิดพลาดและไม่แก้ constraint/RLS ให้เอง
- ตรวจ RLS ของบัญชีกรรมการ/การมอบหมายงานตามคำแนะนำเดิมใน IMPLEMENTATION.md ก่อนให้ใช้บันทึกผลจริง การสมัครและการยืนยันตัวตนไม่ได้ติดตั้ง referee-workflow migration แทนผู้ดูแล
- Ingress ต้องเขียนทับ x-real-ip ที่เชื่อถือได้ โควตาสมัครใช้ RPC เดิม 5 ครั้งต่อ IP ต่อชั่วโมง หากไม่มี header จะใช้โควตาร่วม ไม่เชื่อข้อมูลบทบาทจากผู้สมัคร
- รูปโลโก้เป็น preview ในเครื่องเท่านั้น ประเภทโรงเรียนยังไม่เขียนคอลัมน์ใหม่ลง schools และการปฏิเสธให้ผู้สมัครติดต่อผู้ดูแล ไม่มีการอนุมัติใหม่เอง

## สิ่งที่ตรวจแล้ว

ทดสอบ Route Handlers ด้วย Supabase SDK จริงและ HTTP fixture ตรวจ signup role injection, สิทธิ์ admin ของ API, pending/rejected, legacy login/รหัสผ่านเดิม/ชื่อซ้ำ, การอนุมัติซ้ำและพร้อมกัน, rollback และ recovery รวม E2E ของฟอร์มและเมนูเดิม ใช้ public/service key จำลองใน E2E ไม่ส่งคำขอสมัครหรืออนุมัติไป Supabase จริง

ตรวจ Auth/profiles จริงแบบอ่านอย่างเดียวพบ admin 1 บัญชี และ school_admin 2 บัญชี ในจำนวนนี้โรงเรียน 1 บัญชียังใช้อีเมลเดิม ไม่มีการเปลี่ยนรหัสผ่าน อีเมล บทบาท หรือแถวข้อมูลจริงจากการตรวจนี้ การทดสอบ HTTP concurrency ไม่ใช่หลักฐานการทดสอบหลาย session บน PostgreSQL ที่ hosted จริง

ผลตรวจล่าสุด: Unit/SQL/Route Handler 75 ข้อ และ browser E2E 35 ข้อผ่าน พร้อม TypeScript และ production build แบบ Webpack ตัวแปลง username ตรวจบัญชีจริงแบบอ่านอย่างเดียวแล้วรองรับบัญชีโรงเรียนเดิม 2/2 บัญชีและไม่พบชื่อซ้ำ ยังไม่ได้สมัคร อนุมัติ หรือเขียนข้อมูลทดสอบบนโครงการจริง

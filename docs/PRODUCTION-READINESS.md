# การเปลี่ยนเป็น Supabase จริง · 6 พฤศจิกายน 2569

## ส่วนที่แก้

- `app/page.tsx`: โหลด Supabase ตั้งแต่เปิดเว็บ, ตรวจ session/profile, ล้างข้อมูลส่วนตัวเมื่อเปลี่ยนบัญชี, loading/error/retry และนำ demo/role switch/localStorage ข้อมูลธุรกิจออก
- `components/admin-competition-manager.tsx`, `lib/production-competitions.ts`, `/api/competitions`: สร้างและแก้รายการจริง จัดสาย กำหนดวันเวลา สนาม กรรมการ ตั้งโควตา CSV และกู้การสร้างคู่ที่สะดุด
- `lib/match-results.ts`, `/api/match-results`: ตรวจบัญชีและคู่ที่ได้รับมอบหมายบนเซิร์ฟเวอร์ ตรวจ revision, identity, คะแนน และผู้ชนะคัดออกก่อนบันทึก
- `lib/athletics-results.ts`, `/api/athletics-results`: ตรวจรายการ/นักกีฬา/กรรมการ บันทึกผลและมอบหมายกรรมการผ่านเซิร์ฟเวอร์ คัดรอบชิงจากผล OK ของฮีตที่ได้รับมอบหมาย และใช้ metadata จากฮีตจริง
- `components/school-portal.tsx`, `lib/school-storage.ts`, `/api/schools`, `/api/school-profile`, `/api/coaches`: ชื่อโรงเรียน ประวัติ โลโก้ และผู้ฝึกสอนบันทึกจริง เปิดจากเครื่องอื่นได้ แยกข้อมูลสาธารณะออกจากผู้ติดต่อและโทรศัพท์
- `lib/hosted.ts`: ใช้สถานะ `finished` ตาม constraint จริง (อ่าน `confirmed` เก่าได้), ส่งคอลัมน์วันเวลา/สนามบังคับ และไม่รับทะเบียนใหม่เข้ารายการเก่าที่ไม่ตั้งกติกา
- `lib/referee-review.ts`: บัญชีกรรมการใหม่ได้รับ `referee` เพราะ constraint จริงไม่รับ `recorder` ยังคงรองรับบัญชีเก่าในการตรวจสิทธิ์
- ย้ายข้อมูลสร้างสถานการณ์ทดสอบไป `tests/helpers/sports-fixtures.ts` ลบ UI/demo scripts/parser ที่ไม่มีการใช้งาน และแก้ E2E ให้ใช้ HTTP fixture ของระบบจริง

## โครงสร้างข้อมูล

ไม่เปลี่ยน schema, constraint หรือ RLS และไม่เพิ่มคีย์ลง Git

- ใช้ `competitions.registration_policy` เดิมเพิ่ม `management`: revision, format, teamLimit, details, teams และ fixtures โดยรักษา ruleId/reserves/eventQuotas/maxEventsPerAthlete เดิม
- คู่ที่ยังไม่รู้ทีม หรือยังไม่กำหนดวันเวลา/สนาม อยู่ในโครงสายเท่านั้น เมื่อพร้อมจึงสร้าง `matches` ที่ใช้ UUID จริง ไม่ใส่คู่แข่งหรือเวลาสมมติ
- ประวัติและผู้ฝึกสอนใช้ private Storage `team-files` ตามขอบเขตโรงเรียน/รายการ เป็น immutable JSON พร้อมเวอร์ชัน ไม่ใส่ข้อมูลในคอลัมน์ที่ไม่มีอยู่จริง
- เพิ่ม MIME `application/json` ใน bucket เดิม โดยคง private, ขนาด 2 MB และ MIME CSV/Excel เดิม
- ชื่อ successor คงที่ต่อ predecessor + `upsert:false` ทำให้คำขอพร้อมกันได้หนึ่ง success/หนึ่ง409 พร้อมเก็บประวัติทั้งหมด

## ข้อมูลเดิมและการลบ

สำรวจตารางที่อ้างอิงโรงเรียน/รายการ และตรวจ private Storage ก่อนลบเฉพาะ seed ที่ไม่มีการใช้:

- โรงเรียนตัวอย่างที่ไม่อ้างอิง 9 แห่ง
- รายการตัวอย่าง U12/ผสมที่ไม่อ้างอิง 7 รายการ
- เก็บโรงเรียนตัวอย่าง 1, รายการเปตองเก่า และทะเบียนเดิมที่อ้างอิงไว้ครบ ไม่ย้ายหรือเปลี่ยน UUID
- เก็บโรงเรียนจริง บัญชีจริง และคำขอสมัครเดิมครบ

สำรองแถวที่ลบไว้ใน `.local-backups/unused-seed-1793939995815.json` เฉพาะเครื่อง โฟลเดอร์ถูก ignore ไม่ขึ้น Git ข้อมูลเก่าจากโหมดสาธิตใน localStorage ไม่ถูกนำเข้าฐานข้อมูลโดยอัตโนมัติ เพื่อไม่ให้ชื่อ/บทบาทสมมติปะปนกับข้อมูลจริง

ผู้ดูแลต้องสร้างรายการตามกีฬา/เพศ/ระดับจริง และกำหนดโควตาที่เป็น “ตามผู้จัด” ก่อนเปิดสมัคร ไม่ใช้รายการ U12/ผสมเก่าแทนระเบียบใหม่

## กฎและวิธีทดสอบกีฬา

| ประเภท             | ตัวจริง + สำรอง / รวม | สิ่งที่ทดสอบ                                                              |
| ------------------ | --------------------- | ------------------------------------------------------------------------- |
| ฟุตบอลชาย          | 7+3 /10               | ครบ10ได้ คนที่11ปฏิเสธ และผิดเพศ/ระดับปฏิเสธ                              |
| แชร์บอลหญิง        | 6+ตามผู้จัด           | ยังไม่ตั้งสำรองสมัครไม่ได้ เมื่อตั้งแล้วตรวจเพดานจริง                     |
| วอลเลย์บอลชาย/หญิง | 6+6 /12               | แยกเพศ ตัวจริง/สำรองเกินหรือรวมเกินปฏิเสธ                                 |
| ตะกร้อชาย/หญิง     | 3+2 /5                | แยกเพศและจำนวนตามตำแหน่ง                                                  |
| เปตองชาย/หญิง      | 3+0 /3                | ไม่แสดงสำรอง ปฏิเสธสำรองและคนที่4 พร้อมข้อความห้ามเปลี่ยนตัว              |
| โยนบอลผสมอนุบาล    | 5+ตามผู้จัด           | ตรวจอนุบาลและรอสำรองที่ผู้จัดตั้ง                                         |
| กรีฑาเดี่ยว        | ตามโควตารายการ        | เลือกหลายรายการได้ตาม maxEventsPerAthlete; เกินโควตารายการใดปฏิเสธทั้งชุด |
| วิ่งผลัด           | 4+4 /8                | ตัวจริงไม่เกิน4 สำรองไม่เกิน4 รวมไม่เกิน8                                 |

ข้อมูลเดิมที่ยังไม่จำแนกตำแหน่งใช้พื้นที่โควตาเดิม แต่ไม่ถูกเขียนทับหรือเดาตำแหน่งใหม่ CSV ตรวจทั้งชุดก่อนเพิ่ม เปลี่ยนชื่อทะเบียนเดิมด้วย update ที่รักษาโรงเรียนและรายการ

## หลักฐานการตรวจ

- ผลรอบสุดท้าย: unit/SQL/API 113 ผ่าน, E2E 30 ผ่าน, TypeScript และ production build ผ่าน
- Unit/SQL/API HTTP fixture: `npm test`
- TypeScript: `npm run typecheck`
- E2E production server กับ fixture: `PLAYWRIGHT_TEST_PORT=3100 npx playwright test`
- Build: `npm run build -- --webpack`
- Read-only review และ regression ของการเปลี่ยนผู้ชนะคัดออก/เขียนพร้อมกัน/คัดรอบชิงที่ไม่ผ่านฮีต

ทดสอบ Supabase จริงด้วยข้อมูลชั่วคราวที่แยกจากผู้ใช้เดิม: public read, anonymous ไม่มีทะเบียนส่วนตัว, `school_admin` อ่าน/เพิ่มทะเบียนของตนเองและเพิ่มให้โรงเรียนอื่นไม่ได้, เขียน/อ่าน private JSON, anonymous ดาวน์โหลด private JSON ไม่ได้ และ Storage concurrent save ได้หนึ่ง success/หนึ่ง409 ข้อมูลและบัญชีชั่วคราวถูกลบหลังตรวจ

พบจากระบบจริงว่า client ไม่มี grant เขียนผลแข่งขัน จึงย้ายการบันทึกผลและมอบหมายกรีฑาไป API ที่ตรวจสิทธิ์ก่อนใช้ service role ไม่แก้ grant/RLS เพื่อให้ทดสอบผ่าน ชุดทดสอบ browser จำลองการปฏิเสธ direct write นี้ด้วย

API ผ่าน production server กับ Supabase จริงครบ 11 กรณี: สร้างรายการ จัดสายโดยไม่ใส่เวลาสมมติ ปฏิเสธกรรมการนอกคู่ บันทึกผล `finished` ปฏิเสธการเปลี่ยนผู้ชนะ แสดงข้อมูลสาธารณะโดยไม่เผยผู้ติดต่อ ปฏิเสธกรรมการเข้าประวัติส่วนตัว เปลี่ยนชื่อโรงเรียน ผู้ฝึกสอน ผลกรีฑา และคัดรอบชิงตามฮีตจริง ลบบัญชีและข้อมูลชั่วคราวครบแล้ว

ยืนยันจาก constraint จริงว่า matches ใช้ `finished` และทิศทางกรีฑาใช้ `lower`/`higher` ซึ่งแปลงเป็น `asc`/`desc` บนหน้าจอ ชุด fixture ปฏิเสธ payload ที่ผิดสัญญาจริงเหล่านี้

## ขอบเขตที่ควรรู้

การจัดสายและบันทึกคู่เป็น REST หลายคำขอ สามารถกู้การสร้างคู่ที่ยังไม่สำเร็จได้ แต่ยังไม่มี transaction ครอบคลุมการตั้งเวลาพร้อมกันข้ามคนละรายการ ผู้จัดควรตรวจโปรแกรมรวมก่อนเผยแพร่ ชื่อโรงเรียนกับประวัติเป็นการบันทึกแยกและแจ้งกรณีสำเร็จบางส่วน

การ push โค้ดไม่ได้เพิ่ม environment ให้ hosting เอง ต้องตั้ง URL/public key/server secret บน hosting และใช้ project เดียวกับที่เตรียมรายการจริงไว้ ห้ามเผยแพร่ไฟล์ `.env.local` หรือสำรองข้อมูล

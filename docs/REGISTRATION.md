# รายการแข่งขันและการสมัครนักกีฬา — โรงเรียนบ้านไร่ลำปาง

## สถานะและขอบเขต

ปรับโค้ดและเตรียม additive migration แล้ว **ยังไม่ได้รัน migration บน Supabase จริง** เพราะเซสชันไม่มี administrative database connection ผู้ใช้อนุญาตให้ push โค้ดแล้ว แต่การรันบนฐานข้อมูลจริงยังรอเชื่อม Supabase ผู้ดูแลฐานข้อมูลต้องตรวจ schema จริง สำรองข้อมูล และรันไฟล์ `supabase/migrations/20261104_registration_rosters.sql` บน normalized project ที่ถูกต้อง ไม่ใช้ `supabase/schema.sql` ซึ่งเป็น legacy schema

จำนวนเป็นเพดานต่อโรงเรียนและต่อ competition (แยกกีฬา/เพศ/ระดับชั้น) สมัครทีละคนหรือเป็นชุดได้ ไม่บังคับให้ส่งทีมครบในครั้งเดียว ระดับชั้น/เพศที่ผู้ใช้ไม่ได้ระบุในกติกาให้อ้างอิงรายการแข่งขันของผู้จัด ไม่เดาข้อมูลเพิ่ม

## ส่วนที่แก้ไข

- `lib/registration-rules.json`: แหล่งข้อมูลกติกาชุดกลาง รวมทั้ง 5 รายการกรีฑาเดี่ยวและวิ่งผลัดแยกกัน
- `lib/registration.ts`: เพดาน จำนวนสำรองที่ผู้ดูแลกำหนด การนับ legacy rows โควตารายรายการกรีฑา และตรวจชุดสมัครก่อนบันทึก
- `components/registration-panel.tsx`: ตาราง 7 คอลัมน์ ช่องตัวจริง/สำรองอัตโนมัติ ตั้งค่าโควตา และสรุปรายชื่อพร้อมสถานะ/รายการกรีฑา
- `app/page.tsx`, `app/globals.css`: เชื่อมฟอร์มกับข้อมูลจริง/สาธิต การเลือกประเภท และ responsive/print
- `lib/domain.ts`, `lib/hosted.ts`: optional roster metadata, CSV, ตรวจ schema extension และส่ง metadata โดยไม่เปลี่ยน payload ของระบบเก่าที่ไม่ได้ติดตั้ง extension
- `scripts/generate-registration-migration.ts`: สร้าง SQL catalog จาก JSON เดียวกับหน้าเว็บ
- `tests/registration.test.ts`, `tests/registration-sql.test.ts`, `tests/browser/registration.spec.ts`, `tests/browser/hosted.spec.ts`: domain/database/browser regressions

## โครงสร้างข้อมูล

เพิ่มโดยไม่ลบหรือเปลี่ยนชื่อคอลัมน์/IDs เดิม:

1. `competitions.registration_policy jsonb` nullable

   ```json
   {"ruleId":"football-male","reserves":3,"eventQuotas":{},"maxEventsPerAthlete":null}
   ```

   ตัวเลขสำรองตายตัวอ้างอิง catalog เท่านั้น ผู้ดูแลตั้งค่าเฉพาะประเภทที่ระบุ “ตามระเบียบผู้จัด” กรีฑาเดี่ยวใช้ `eventQuotas` เช่น `{"run60":2,"run100":3}` และเลือกกำหนดเพดานรายการต่อคนเพิ่มเติมได้ ช่อง quota ว่างหมายถึงยังไม่เปิดสมัคร; 0 หมายถึงไม่มีที่รับสมัคร

2. `registrations.roster_details jsonb` nullable

   ```json
   {"ruleId":"athletics-individual","position":"individual","events":["run60","run100"]}
   ```

   `position` ที่เก็บจริงคือ `starter`, `reserve`, `individual` เท่านั้น `auto` เป็นสถานะชั่วคราวตอนอ่าน CSV และถูกจัดช่อง/ตรวจให้เสร็จก่อนเขียน ข้อมูลเดิมเป็น SQL NULL และไม่เดาสถานะให้

3. `registration_rule_catalog`: ข้อมูลสาธารณะ ไม่มีรายชื่อนักกีฬา; anon/authenticated อ่านได้แต่แก้ไขไม่ได้ Seed สร้างจาก JSON และมี database test เทียบกับแหล่งข้อมูลกลาง

4. เพิ่ม validating triggers บน competitions/registrations ไม่มีการเปลี่ยน RLS/policies หรือ constraints เดิม การเขียนยังต้องผ่าน RLS เดิมเสมอ Trigger ตรวจบทบาท/โรงเรียน โควตา และใช้ transaction lock กับ school+competition เพื่อให้คำขอไม่ต่างคนต่างนับช่องว่างโดยไม่ประสานกัน ทดสอบใน PGlite แล้ว แต่ยังไม่ใช่ผลทดสอบ concurrent sessions บน hosted PostgreSQL จริง

โหมดสาธิตคงข้อมูล `kosamphi-demo-v1` เดิม และแยก settings ที่ `kosamphi-registration-policies-v1` ไม่ส่งไป Supabase

## กฎตรวจสอบ

| ประเภท | ตัวจริง | สำรอง | สูงสุด |
|---|---:|---:|---:|
| ฟุตบอลชาย 7 คน | 7 | 3 | 10 |
| แชร์บอลหญิง | 6 | ผู้ดูแลตั้งภายหลัง | 6 + ค่าที่ตั้ง |
| วอลเลย์บอลชาย/หญิง แยกคนละรายการ | 6 | 6 | 12 |
| ตะกร้อชาย/หญิง ทีมเดี่ยว แยกคนละรายการ | 3 | 2 | 5 |
| เปตองทีมชาย/หญิง แยกคนละรายการ | 3 | 0 | 3 |
| โยนบอลผสม อนุบาล | 5 | ผู้ดูแลตั้งภายหลัง | 5 + ค่าที่ตั้ง |
| กรีฑาเดี่ยว | ตาม quota ของแต่ละ event | ไม่มี | ตามผู้จัด |
| วิ่งผลัด | 4 | ไม่เกิน 4 | 8 |

- ฟุตบอล วอลเลย์บอล และแชร์บอลใช้ประถมศึกษา/มัธยมศึกษา; โยนบอลใช้อนุบาล
- ตรวจจำนวนรวม ตัวจริง และสำรอง แยกกัน ไม่ใช้จำนวนรวมแทนการตรวจตำแหน่ง
- เปตองไม่สร้างช่องสำรอง แสดง “ไม่มีการเปลี่ยนตัวระหว่างเกม”
- แชร์บอล/โยนบอลที่ยังไม่ตั้งจำนวนสำรองยังไม่เปิดส่งฟอร์ม ไม่เดาว่าเป็น 0 หรือไม่จำกัด
- กรีฑาเดี่ยวเลือกได้หลายรายการจาก 60/80/100/200 เมตร/มินิมาราธอน ต้องมีโควตาของทุกรายการที่เลือก และไม่มีรายการซ้ำหรือ null
- วิ่งผลัดเป็นคนละประเภทกับกรีฑาเดี่ยว จึงเลือกสมัครบุคคลเดียวกันเพิ่มเติมได้โดยอ้างอิงคนละรายการ ไม่รวมเพดานวิ่งผลัดกับกรีฑาเดี่ยว
- ชื่อ/bib ซ้ำในโรงเรียนและรายการเดียวกันถูกปฏิเสธ รายชื่อชุดที่เกินถูกปฏิเสธก่อนการเขียน; SQL insert หลายแถวที่มีแถวผิดพลาดจะ rollback ทั้งคำขอ
- ผู้ดูแลปรับสำรองที่ไม่ตายตัวได้ 0–100 คน และโควตาราย event 0–100 คน ค่า 100 เป็นขอบเขตของหน้าตั้งค่าปัจจุบัน ไม่ใช่กติกาการแข่งขันที่อนุมานเพิ่ม
- คงข้อความกำกับที่ผู้ใช้ระบุใต้ตารางกติกาและส่วนท้ายแบบฟอร์ม

## ข้อมูลเดิมที่ต้องตรวจทาน

**ไม่ต้องย้าย** `registrations`, IDs, names, school IDs, bib, matches, results หรือ medals ไปตารางใหม่ Migration ไม่ลบ/เขียนทับรายชื่อเดิม และไม่สร้าง competition ใหม่โดยเดาค่าคอลัมน์ที่ project อาจบังคับ

สิ่งที่ผู้จัดต้องตรวจ:

1. รายการทีมที่กีฬา/เพศ/ระดับตรงกับ catalog ผูก policy ให้อัตโนมัติ โดยไม่แก้ข้อมูลผู้สมัคร กรณีไม่ตรง เช่น U12 หรือฟุตบอลผสม คงเป็นรายการเก่า ผู้จัดต้องตรวจว่าเทียบชั้นใด/เพศใดจริงแล้วเตรียมรายการที่ถูกต้อง ห้ามเปลี่ยนประวัติเพศ/ระดับของรายการที่มีผู้สมัครเพื่อบังคับให้ตรง
2. กรีฑาเดิมที่รวมหลายประเภทต้องเตรียม competition สำหรับประเภทเดี่ยวและวิ่งผลัดแยกกัน แล้วผูก rule ที่ถูกต้องผ่านหน้าตั้งค่าผู้ดูแล (หรือ trusted SQL ตาม permissions เดิม)
3. รายชื่อที่ `roster_details IS NULL` แสดง “ข้อมูลเดิม · ยังไม่ระบุตัวจริง/สำรอง” และนับรวมเพดานทีม ผู้จัดต้องยืนยันสถานะจากใบสมัครก่อนเติม metadata โดย update เฉพาะ ID เดิม ห้ามจัดสถานะจากลำดับชื่อ/เวลา/UUID เอง
4. กรีฑาเดิมที่ไม่ทราบ event จะบล็อกการสมัครกรีฑาเดี่ยวเพิ่มใน school+competition นั้นจนตรวจทาน เพราะยังคำนวณโควตาคงเหลือไม่ได้ ห้ามเดาว่าทุกรายการว่าง
5. ทีมเดิมที่เกินเพดานใหม่คงอยู่ทั้งหมด แต่สมัครเพิ่มไม่ได้ ผู้จัดต้องตัดสินสถานะตามระเบียบ ไม่ลบส่วนเกินอัตโนมัติ
6. ปิงปองและรายการเก่าอื่นที่ไม่อยู่ในรายการใหม่ยังเปิดดูได้ ไม่ลบข้อมูลหรือผลแข่ง และไม่เปิดแบบฟอร์มใหม่ให้กับประเภทที่ไม่อยู่ใน catalog
7. CSV เดิมแบบ `name,school_id,sport,gender,division,bib` ยังอ่านได้ กีฬาทีมที่มี rule ชัดเจนจะเติมช่องตัวจริงก่อนสำรองเฉพาะ **แถวใหม่** ถ้าให้ `position` มา จะตรวจตามที่ระบุ ไม่ย้ายสำรองให้เอง กรีฑาต้องเพิ่ม `rule_id`, `position`, `events` (`run60|run100` เป็นต้น)

หลัง migration ให้ refresh schema cache (ไฟล์มี `notify pgrst`) และโหลดข้อมูลใหม่ในแอป หาก RLS เดิมไม่อนุญาตให้ admin แก้ competitions การตั้งค่าในเว็บจะถูกปฏิเสธอย่างชัดเจน ใช้ผู้ดูแลฐานข้อมูลตั้ง policy แทน ไม่ข้าม RLS หรือใช้ service key ใน browser

## วิธีทดสอบ

รัน `npm test`, `npm run typecheck`, `npm run build` และ Playwright ผ่าน browser fixture แยก ไม่เขียนข้อมูลทดสอบเข้า project จริง

| กรณี | วิธีทดสอบที่ควรผ่าน |
|---|---|
| ฟุตบอล | กรอก 7 ตัวจริง + 3 สำรอง บันทึกได้; เพิ่มคนที่ 11 หรือคนตัวจริงที่ 8 ไม่ได้ |
| วอลเลย์บอลชาย/หญิง | ทดสอบคนละประเภท 6+6 ผ่าน; คนที่ 13/ตัวจริงคนที่ 7 ถูกปฏิเสธ |
| ตะกร้อชาย/หญิง | ทดสอบคนละประเภท 3+2 ผ่าน; คนที่ 6/ตัวจริงคนที่ 4 ถูกปฏิเสธ |
| เปตองชาย/หญิง | มีช่องตัวจริง 3 ไม่มีช่องสำรอง; ส่ง reserve ผ่าน API ถูกปฏิเสธ |
| แชร์บอล | ก่อนตั้งค่าสำรองส่งไม่ได้; ตั้ง 2 แล้วมี 8 ช่อง; แถวที่ 9 ไม่ได้ |
| โยนบอล | เลือกแล้วเป็นผสม/อนุบาล; ก่อนตั้งสำรองส่งไม่ได้; ตั้ง 2 ได้สูงสุด 7 คน |
| กรีฑาเดี่ยว | ตั้ง run60=1/run100=2 เลือกสองรายการให้คนเดียวได้; คนที่สองลง run60 ไม่ได้; quota ว่าง/0, event ซ้ำ/ไม่รู้จัก/null ถูกปฏิเสธ |
| วิ่งผลัด | ตัวจริง 4 + สำรอง 4 ผ่าน; คนที่ 9 หรือสำรองที่ 5 ไม่ได้ |
| CSV | 11 แถวฟุตบอลถูกปฏิเสธทั้งชุด; rule_id มีแต่ไม่มี position จัด 7+3 เฉพาะแถวใหม่ได้; ต่างโรงเรียนถูกปฏิเสธใน school_admin |
| ข้อมูลเก่า | เก็บ ID/bib เดิม metadata ยัง null; คนนับเข้าเพดานโดยไม่เขียนทับ; schema ยังไม่ migrate แสดงข้อความ compatibility |
| สิทธิ์/ฐานข้อมูล | school_admin โรงเรียนตนเองผ่าน; โรงเรียนอื่น/บัญชีไม่ผูกโรงเรียน/ตั้ง policy โดย non-admin ถูกปฏิเสธ; static catalog เขียนผ่าน anon/authenticated ไม่ได้ |
| หน้าจอ | 390/820/1440px ตารางเลื่อนภายใน ช่องแบบฟอร์มไม่ล้นจอ; keyboard ใช้งานได้; พิมพ์/PDF มีตารางและรายชื่อ ไม่มีช่องกรอก |

การตรวจ live ก่อนเปิดใช้งานยังต้องครอบคลุม schema/policies จริงและ concurrent transactions บน hosted PostgreSQL โดยผู้ดูแล project เอกสารกลไกที่ใช้อ้างอิง: [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html) และ [security-definer functions](https://www.postgresql.org/docs/current/sql-createfunction.html)

# นครโกสัมพีเกมส์ · ปีการศึกษา 2569

Next.js App Router + TypeScript + Tailwind CSS + Supabase รองรับโรงเรียนที่ลงทะเบียน และฟุตบอล วอลเลย์บอล แชร์บอล เปตอง เซปักตะกร้อ กรีฑา โยนบอล ปิงปอง

## หน้าตาขาว–ทอง

ใช้แนวทาง B ที่เลือกไว้: hero ขนาดใหญ่ ภาพกีฬา Perspective Tunnel, ฟอนต์ Sarabun ที่เก็บในโปรเจกต์ และไอคอน Lucide รองรับ reduced motion และการเลื่อนหน้าปกติ เมนูมือถือแสดงหน้าตามบทบาท พร้อม focus/ปุ่มปิด/Escape และปิดอัตโนมัติเมื่อเปลี่ยนเป็น desktop

โครงสร้าง UI อยู่ที่ `components/ui` โดยมี `perspective-tunnel-hero.tsx`, `button.tsx`, `demo.tsx` และ `lib/utils.ts` ใช้ alias `@/*` → root ของโปรเจกต์ ตั้งค่า shadcn ไว้ใน `components.json` แล้ว จึงไม่ต้องรัน `init` ซ้ำ Styles หลักและ theme tokens อยู่ที่ `app/globals.css` ไม่ต้องติดตั้ง TypeScript หรือ Tailwind เพิ่ม

dependencies ใหม่ติดตั้งพร้อม `npm ci` ได้แก่ Framer Motion, Lucide, clsx, tailwind-merge และ class-variance-authority ข้อมูลและสิทธิ์ยังใช้ระบบเดิมทั้งหมด ภาพ sports จาก Unsplash และฟอนต์ Sarabun พร้อม OFL อยู่ใน `public/` ไม่มีการเรียก CDN ระหว่างใช้งาน

ถ่ายภาพตรวจแบบซ้ำได้ขณะเปิดเว็บด้วย `npx tsx scripts/capture-design.ts` (ใช้ Chrome บน macOS หรือกำหนด `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`; URL เริ่มต้น `http://127.0.0.1:3000` เปลี่ยนได้ด้วย `DESIGN_PREVIEW_URL`) สคริปต์สร้างข้อมูลสาธิตใน localStorage ของ browser context แยก ไม่เขียน Supabase ผลลัพธ์อยู่ที่ `docs/design-review/`

## เริ่มใช้งาน

Node.js 24, npm 11

```sh
npm ci
npm run dev
```

โหมดสาธิตเริ่มต้นโดยไม่ต้องมีคีย์ เก็บข้อมูลเฉพาะ localStorage ของเบราว์เซอร์และไม่มีโรงเรียนตัวอย่าง เลือกบทบาทจากเมนูโปรไฟล์ด้านบนของหน้าแรกเพื่อสลับเข้ามุมมองผู้ชม ผู้ดูแลระบบ โรงเรียน หรือกรรมการได้ทันที ระบบล็อกอินจริงจะจัดการในภายหลัง ส่วนหน้าลงทะเบียนโรงเรียนยังเป็น UI preview ไม่ส่งข้อมูล

## Supabase ปัจจุบัน

เว็บปรับให้ใช้โครงสร้าง normalized ของฐานข้อมูลที่ผู้ใช้เตรียมไว้แล้ว **ไม่ต้องลบตารางหรือรัน `supabase/schema.sql` ซ้ำ** ไฟล์นั้นและ `verify-rls.sql` เป็น legacy สำหรับสัญญาข้อมูลเก่า ไม่ใช่ migration ของรุ่นนี้

| ข้อมูลในเว็บ                      | ตารางจริง                                   |
| --------------------------------- | ------------------------------------------- |
| โรงเรียน                          | `schools` (รหัส UUID)                       |
| รายการแข่งขัน/รุ่น/เพศ/กติกาคะแนน | `competitions`                              |
| ลงทะเบียนนักกีฬา                  | `registrations`                             |
| ตารางแข่งขัน/ผลทีม                | `matches` เชื่อม `competition_id`           |
| รายการกรีฑา/ฮีต/รอบชิง            | `athletics_events`                          |
| ผลกรีฑา                           | `athletics_results` เชื่อมโรงเรียนและ `bib` |
| เหรียญ                            | `medals`                                    |
| บัญชี/สิทธิ์                      | `profiles` เชื่อม Supabase Auth             |

คอลัมน์ที่อ่านและเขียนอยู่ใน `lib/hosted.ts` เว็บไม่สร้างรายการ `competitions` อัตโนมัติ ให้ผู้ดูแลเตรียมรายการผ่านระบบฐานข้อมูลที่ใช้อยู่ แล้วเลือกชื่อรายการในเว็บ (เช่น U12 / ผสม) ไม่สร้างหรือแก้ `team_files` ในงานปรับครั้งนี้

1. ตั้ง `NEXT_PUBLIC_SUPABASE_URL` และ `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` **หรือ** `NEXT_PUBLIC_SUPABASE_ANON_KEY` ผ่าน environment settings
2. หากกำหนดทั้งสองคีย์ เว็บจะใช้ `PUBLISHABLE_KEY` ก่อน ใช้เฉพาะ publishable/anon key ห้ามใช้ service-role key ในเว็บหรือ Git
3. Restart dev server หรือ build ใหม่ แล้วเปิดเมนู **โรงเรียน / บัญชี**
4. เข้าสู่ระบบด้วยบัญชี Supabase Auth ที่ผู้ดูแลกำหนด profile ไว้แล้ว ไม่สร้างบัญชีหรือกำหนดสิทธิ์ตนเองจาก client

ระบบรองรับบทบาท `admin`, `recorder`, `referee`, `school`, `school_admin` และผู้ชม ผู้ไม่มี profile เป็นผู้ชม ผู้ชมเห็นเฉพาะภาพรวม ตารางแข่งขัน ตารางคะแนน และเหรียญรางวัล ในโหมดสาธิตสามารถสลับมุมมองบทบาทได้ทันทีเพื่อทดลองหน้าจอ โดยยังไม่ยืนยันตัวตนและไม่ถือเป็นการควบคุมสิทธิ์จริง เมื่อใช้ Supabase สิทธิ์จริงมาจาก profile/RLS เท่านั้น `school_admin` อ่านทะเบียน/ลงทะเบียนและเลือก CSV ได้เฉพาะโรงเรียนตนเอง

หน้า **จัดการรายการแข่งขัน** แสดงเฉพาะผู้ดูแลระบบ มีฟอร์มตั้งชื่อ/รายละเอียด ชนิดกีฬา ระดับ เพศ โควตาผู้เล่น รูปแบบคัดออกหรือพบกันหมด และคะแนน พร้อมต้นแบบจัดทีมลงสายด้วยลากวางหรือ dropdown และนำเข้ารายการแข่งขัน ทีม หรือตารางจาก CSV โดยตรวจตัวอย่างก่อนยืนยัน ไฟล์ตัวอย่างมีให้ดาวน์โหลดจากหน้าเดียวกัน ปุ่มล้างข้อมูลลบรายการ ทีม และตารางทั้งหมดของต้นแบบนี้หลังยืนยัน ไม่กระทบข้อมูลสาธิตส่วนอื่น ขณะนี้เป็น UI ต้นแบบ ข้อมูลเก็บแยกใน localStorage ของเบราว์เซอร์ ไม่ได้เขียน Supabase หรือแก้ผลจริง

**ยังต้องทดสอบ login และการเขียนด้วยบัญชีแต่ละสิทธิ์ใน project จริง** คีย์สาธารณะยืนยันได้เฉพาะการอ่านในฐานะผู้ชม ไม่มีการอนุมานว่า RLS ปลอดภัยจากการเห็นตารางว่าง ใช้ `supabase/inspect-hosted.sql` เพื่อตรวจ RLS/policies/check constraints แบบอ่านอย่างเดียวได้ ไม่มี privileged credentials ใน repo

## สมัครโรงเรียนด้วยชื่อบัญชี — UI preview

หน้า `/school-registration` แสดงตัวอย่างฟอร์มชื่อบัญชี/รหัสผ่าน ชื่อโรงเรียน ประเภทโรงเรียน ชื่อผู้บริหาร และตราโรงเรียน รูปภาพแสดง preview ใน browser เท่านั้น การกดปุ่มจะแสดงสรุปและไม่สร้างบัญชี ไม่ส่งคำขอ หรือบันทึกข้อมูล Backend สำหรับการสมัครมีอยู่ แต่ UI ปัจจุบันยังไม่เรียกใช้งาน

หน้าเหรียญรางวัลคำนวณจากผลที่กรรมการยืนยัน ไม่เพิ่มเหรียญด้วยมือ: รอบชิงใช้ผลผู้ชนะ/รองชนะเลิศ, ชิงอันดับ 3 ใช้ผลผู้ชนะ, และพบกันหมดใช้ตารางคะแนนเมื่อทุกคู่ในสายเดียวกันเสร็จ กรีฑาใช้ผลรอบชิงอันดับ 1–3 เหรียญเดิมยังเก็บไว้แต่ไม่นำมารวมยอด โรงเรียนแยกกลุ่มขนาดเล็ก/ขยายโอกาสได้เมื่อประเภทถูกบันทึกในข้อมูลโรงเรียนจริง; โรงเรียนเดิมที่ยังไม่ระบุอยู่ในยอดรวมเท่านั้น ปัจจุบันฟอร์มลงทะเบียนและประเภทโรงเรียนยังเป็นตัวอย่าง UI ไม่บันทึกข้อมูล

- ก่อนเปิดใช้ UI นี้ ให้เชื่อมฟอร์มกับ backend และตรวจ schema/สิทธิ์ตามขั้นตอน
- ตั้ง `SUPABASE_SERVICE_ROLE_KEY` เป็น **server-only environment variable** ใน Vercel/secret manager เพื่อให้ `/api/school-account` สร้าง Supabase Auth user ได้ ห้ามใช้ prefix `NEXT_PUBLIC_`, ห้ามส่งคีย์ให้ browser, และห้าม commit คีย์หรือสร้าง `.env.local` ให้ ตั้งเฉพาะ environment ที่ต้องใช้งาน
- Backend ใช้ `x-real-ip` จาก trusted hosting ingress เพื่อจำกัดการสร้างบัญชีไม่เกิน 5 ครั้งต่อ IP ต่อชั่วโมงแบบ atomic ในฐานข้อมูล ตั้งค่า reverse proxy ให้เขียนทับ header นี้ และอย่าเปิด backend ตรงจาก proxy ที่เชื่อ header จาก client
- บัญชีภายในใช้ email alias ที่สงวนไว้ (`accounts.sports-competition.invalid`) เพื่อให้ Supabase Auth ยังคงออก session สำหรับ RLS ได้ ผู้สมัครไม่ต้องมีหรือกรอกอีเมล ระบบยืนยัน alias ภายในตอนสร้างบัญชี
- ใช้ migration `supabase/migrations/20261105_school_registration.sql` หลังตรวจ schema จริงก่อนรัน ไฟล์นี้เพิ่มตารางคำขอและ rate limit, RLS เฉพาะแถวเจ้าของ/admin และ RPC ที่อนุมัติได้เฉพาะ admin โดยสร้าง `schools` กับ `profiles(role='school_admin', school_id=...)` ใน transaction เดียว ไม่แก้ตาราง/นโยบาย/ข้อมูลเดิม migration จะหยุดหากชนิดคอลัมน์ schema จริงไม่ตรงกับ normalized contract
- Admin เข้าสู่โหมด Supabase ที่เมนู **โรงเรียน / บัญชี** แล้วโหลด/ตรวจคำขอ การปฏิเสธบันทึกสถานะและหมายเหตุโดยไม่สร้างโรงเรียนหรือ profile ผู้สมัครแก้และส่งคำขอใหม่ได้ ส่วนการอนุมัติจะ rollback ทั้งหมดหาก constraint เดิมไม่ยอมรับข้อมูล
- ต้องตั้งค่า URL, public key และ service-role secret ใน deployment environment แล้ว deploy migration ก่อนเปิดใช้หน้า การเปลี่ยนโค้ดอย่างเดียวไม่เปิดใช้ฟีเจอร์ใน Production

## ลงทะเบียนและ CSV

- เลือกรายการแข่งขันที่มีอยู่ก่อนลงทะเบียนรายคน
- เพิ่ม `bib` ได้ หากเว้นว่าง ระบบใช้ UUID ของทะเบียนเป็น bib อัตโนมัติในโหมดจริง ผลกรีฑาจับคู่ด้วย **รายการแข่งขัน + โรงเรียน + bib** ต้องไม่ซ้ำในขอบเขตนี้
- CSV UTF-8 หัว `name,school_id,sport,gender,division,bib` (`bib` ไม่บังคับ) ขนาดไม่เกิน 2 MB
- โหมดจริงใช้ school UUID หรือชื่อโรงเรียนที่ตรงและไม่ซ้ำ ไม่ใช้ลำดับแถว 1–10 แทน UUID กด **ดาวน์โหลดแบบฟอร์ม CSV** และ **ดาวน์โหลดรหัสโรงเรียน** จากหน้าเว็บเพื่อใช้ค่าปัจจุบัน
- CSV ต้องระบุกีฬา/รุ่น/เพศตรงกับรายการจริง การจับคู่ที่ไม่พบหรือกำกวมจะถูกปฏิเสธ ไม่มีการสร้างรายการให้เอง การนำเข้าผ่าน RLS ของผู้ใช้ที่เข้าสู่ระบบอยู่

## การแข่งขันและผล

- สร้างสายพบกันหมดจากโรงเรียนที่เลือก แยกตาม competition และสาย แล้วกำหนดวันเวลา/สนามรายคู่
- วันเวลาบนฟอร์มเป็น **Asia/Bangkok** เสมอ แปลงเป็น timestamptz UTC เมื่อบันทึก ค่าว่างส่ง `null`
- ตารางทีมใช้คะแนนจำนวนเต็มไม่ติดลบ การยืนยันผลส่ง status `finished` ตารางคะแนนใช้ `win_points`, `draw_points`, `loss_points` ของรายการนั้น และไม่รวมคะแนน `null` หรือคู่ที่ยังไม่จบ
- การแก้ตาราง/ผลเดิมตรวจ `revision` และเพิ่มครั้งละ 1 ถ้าคนอื่นแก้ไปแล้วจะปฏิเสธ ให้กด **โหลดข้อมูลใหม่** ในเมนูบัญชีก่อนแก้ใหม่ ไม่เขียนทับเงียบ ๆ
- กรีฑาเลือกรายการที่มีอยู่เพื่อรักษา kind/direction/unit และ metadata เดิม หรือกรอกชื่อ/รอบ/ฮีตเพื่อสร้างรายการเมื่อบันทึกผล รองรับ `track`/`field`, `asc`/`desc`, `heat`/`final` และ `OK`/`DNS`/`DNF`/`DQ` ค่าผลต้องมากกว่า 0 เมื่อ OK
- ชื่อรายการและรอบซ้ำต้องเลือก event ID ให้ชัดเจน คัดเข้ารอบชิงด้วยผู้มีสิทธิ์ ผู้ได้ผลเท่ากันได้อันดับร่วม ไม่สร้างเหรียญจากฮีตอัตโนมัติ
- ผู้ชมที่ไม่มีสิทธิ์เห็นทะเบียนนักกีฬา ยังเห็นผลสาธารณะเป็นโรงเรียน/bib ตาม RLS ได้ เมื่อ bib จับคู่ทะเบียนไม่ได้หรือซ้ำ เว็บไม่เลือกนักกีฬาให้เอง
- หากสร้าง event สำเร็จแต่เขียน result ไม่สำเร็จ อาจมีรายการกรีฑาที่ยังว่างเหลืออยู่ ระบบไม่ลบ event หรือผลอื่นเพื่อแก้ข้อผิดพลาด ให้แก้สิทธิ์แล้วบันทึกซ้ำ
- เหรียญส่ง `gold`/`silver`/`bronze` ลง `medals` ของ competition ที่เลือก กติกา/check constraints และ RLS ในฐานข้อมูลยังเป็นตัวบังคับสุดท้าย
- พิมพ์/PDF ผ่าน browser เลือก Save as PDF ใช้ A4 แนวนอนและฟอนต์ไทยในเครื่อง ไม่ใช่บริการสร้าง PDF บน server

## ตรวจสอบ

```sh
npm test
npm run typecheck
npm run build
npm run test:e2e
```

E2E ใช้ `/usr/bin/chromium` หากมี, Chrome บน macOS หรือกำหนด `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` ทดสอบโหมดสาธิตและ hosted API fixture รวมการเขียน normalized payload, school UUID, pagination, revision, กรีฑาฮีต/รอบชิง และการแยก localStorage พร้อม hero, reduced motion, เมนูมือถือ/การหมุนจอ, loading/success/error และ PDF ไม่มีการส่ง write ทดสอบไปฐานข้อมูลจริง การทดสอบ RLS ใน PGlite ครอบคลุม **legacy schema เท่านั้น** ไม่ใช่หลักฐานยืนยันนโยบาย hosted project ปัจจุบัน

การตรวจ project จริงใช้คำขออ่านอย่างเดียว ไม่แก้ข้อมูลเพื่อทดสอบ ประเด็นที่ยังต้องตรวจด้วยบัญชีจริงคือ constraints/บทบาทที่ไม่ปรากฏใน column metadata, การเขียนตามสิทธิ์, การแก้พร้อมกัน และเวลาที่ session หมดอายุ

เก็บเฉพาะ `.env.example` ที่ไม่มีค่า ห้าม commit `.env.local`, คีย์ หรือไฟล์ build ตรวจ GitHub main ให้เรียบร้อยก่อนเชื่อม hosting การ push โค้ดไม่ได้ตั้งค่าหรืออนุญาตการเผยแพร่เว็บใหม่ งานนี้ไม่เปลี่ยนฐานข้อมูลหรือเผยแพร่เว็บ

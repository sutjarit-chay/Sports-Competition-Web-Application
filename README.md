# นครโกสัมพีเกมส์ · ปีการศึกษา 2569

Next.js App Router + TypeScript + Tailwind CSS + Supabase รองรับ 10 โรงเรียน และฟุตบอล วอลเลย์บอล แชร์บอล เปตอง เซปักตะกร้อ กรีฑา โยนบอล ปิงปอง

## เริ่มใช้งาน

Node.js 24, npm 11

```sh
npm ci
npm run dev
```

โหมดสาธิตเริ่มต้นโดยไม่ต้องมีคีย์ เก็บข้อมูลเฉพาะ localStorage ของเบราว์เซอร์ ใช้โรงเรียนชั่วคราว 1–10 สามารถทดลองลงทะเบียน CSV จัดสาย ตารางแข่ง บันทึกผล กรีฑา ตารางคะแนน เหรียญ และ PDF ได้

## Supabase ปัจจุบัน

เว็บปรับให้ใช้โครงสร้าง normalized ของฐานข้อมูลที่ผู้ใช้เตรียมไว้แล้ว **ไม่ต้องลบตารางหรือรัน `supabase/schema.sql` ซ้ำ** ไฟล์นั้นและ `verify-rls.sql` เป็น legacy สำหรับสัญญาข้อมูลเก่า ไม่ใช่ migration ของรุ่นนี้

| ข้อมูลในเว็บ                      | ตารางจริง                                   |
| --------------------------------- | ------------------------------------------- |
| โรงเรียน                          | `schools` (รหัส UUID)                       |
| รายการแข่งขัน/รุ่น/เพศ/กติกาคะแนน | `competitions`                              |
| ลงทะเบียนนักกีฬา                  | `registrations`                             |
| ตารางแข่งขัน/ผลทีม                | `matches` เชื่อม `competition_id`           |
| รายการกรีฑา/ฮีต/รอบชิง            | `athletics_events`                          |
| ผลกรีฑา                           | `athletics_results` เชื่อมโรงเรียนและ `bib` |
| เหรียญ                            | `medals`                                    |
| บัญชี/สิทธิ์                      | `profiles` เชื่อม Supabase Auth             |

คอลัมน์ที่อ่านและเขียนอยู่ใน `lib/hosted.ts` เว็บไม่สร้างรายการ `competitions` อัตโนมัติ ให้ผู้ดูแลเตรียมรายการผ่านระบบฐานข้อมูลที่ใช้อยู่ แล้วเลือกชื่อรายการในเว็บ (เช่น U12 / ผสม) ไม่สร้างหรือแก้ `team_files` ในงานปรับครั้งนี้

1. ตั้ง `NEXT_PUBLIC_SUPABASE_URL` และ `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` **หรือ** `NEXT_PUBLIC_SUPABASE_ANON_KEY` ผ่าน environment settings หรือ `.env.local` ที่ถูก Git ignore
2. หากกำหนดทั้งสองคีย์ เว็บจะใช้ `PUBLISHABLE_KEY` ก่อน ใช้เฉพาะ publishable/anon key ห้ามใช้ service-role key ในเว็บหรือ Git
3. Restart dev server หรือ build ใหม่ แล้วเปิดเมนู **โรงเรียน / บัญชี → เข้าสู่โหมด Supabase**
4. เข้าสู่ระบบด้วยบัญชี Supabase Auth ที่ผู้ดูแลกำหนด profile ไว้แล้ว ไม่สร้างบัญชีหรือกำหนดสิทธิ์ตนเองจาก client

เว็บรู้จักบทบาท `admin`, `recorder`, `referee`, `school` และผู้ชม ผู้ไม่มี profile เป็นผู้ชม การอนุญาตจริงขึ้นกับ RLS ของฐานข้อมูล ผู้ประสานงานต้องมี `profiles.school_id` เป็น UUID ของโรงเรียนจริง กรรมการที่ RLS จำกัดเฉพาะรายการที่รับผิดชอบจะถูกปฏิเสธเมื่อเขียนรายการอื่น เว็บแสดงข้อผิดพลาดจากฐานข้อมูลโดยไม่ข้ามสิทธิ์

**ยังต้องทดสอบ login และการเขียนด้วยบัญชีแต่ละสิทธิ์ใน project จริง** คีย์สาธารณะยืนยันได้เฉพาะการอ่านในฐานะผู้ชม ไม่มีการอนุมานว่า RLS ปลอดภัยจากการเห็นตารางว่าง ใช้ `supabase/inspect-hosted.sql` เพื่อตรวจ RLS/policies/check constraints แบบอ่านอย่างเดียวได้ ไม่มี privileged credentials ใน repo

## ลงทะเบียนและ CSV

- เลือกรายการแข่งขันที่มีอยู่ก่อนลงทะเบียนรายคน
- เพิ่ม `bib` ได้ หากเว้นว่าง ระบบใช้ UUID ของทะเบียนเป็น bib อัตโนมัติในโหมดจริง ผลกรีฑาจับคู่ด้วย **รายการแข่งขัน + โรงเรียน + bib** ต้องไม่ซ้ำในขอบเขตนี้
- CSV UTF-8 หัว `name,school_id,sport,gender,division,bib` (`bib` ไม่บังคับ) ขนาดไม่เกิน 2 MB
- โหมดจริงใช้ school UUID หรือชื่อโรงเรียนที่ตรงและไม่ซ้ำ ไม่ใช้ลำดับแถว 1–10 แทน UUID กด **ดาวน์โหลดแบบฟอร์ม CSV** และ **ดาวน์โหลดรหัสโรงเรียน** จากหน้าเว็บเพื่อใช้ค่าปัจจุบัน
- CSV ต้องระบุกีฬา/รุ่น/เพศตรงกับรายการจริง การจับคู่ที่ไม่พบหรือกำกวมจะถูกปฏิเสธ ไม่มีการสร้างรายการให้เอง การนำเข้าผ่าน RLS ของผู้ใช้ที่เข้าสู่ระบบอยู่

## การแข่งขันและผล

- สร้างสายพบกันหมดจากโรงเรียนที่เลือก แยกตาม competition และสาย แล้วกำหนดวันเวลา/สนามรายคู่
- วันเวลาบนฟอร์มเป็น **Asia/Bangkok** เสมอ แปลงเป็น timestamptz UTC เมื่อบันทึก ค่าว่างส่ง `null`
- ตารางทีมใช้คะแนนจำนวนเต็มไม่ติดลบ การยืนยันผลส่ง status `finished` ตารางคะแนนใช้ `win_points`, `draw_points`, `loss_points` ของรายการนั้น และไม่รวมคะแนน `null` หรือคู่ที่ยังไม่จบ
- การแก้ตาราง/ผลเดิมตรวจ `revision` และเพิ่มครั้งละ 1 ถ้าคนอื่นแก้ไปแล้วจะปฏิเสธ ให้กด **โหลดข้อมูลใหม่** ในเมนูบัญชีก่อนแก้ใหม่ ไม่เขียนทับเงียบ ๆ
- กรีฑาเลือกรายการที่มีอยู่เพื่อรักษา kind/direction/unit และ metadata เดิม หรือกรอกชื่อ/รอบ/ฮีตเพื่อสร้างรายการเมื่อบันทึกผล รองรับ `track`/`field`, `asc`/`desc`, `heat`/`final` และ `OK`/`DNS`/`DNF`/`DQ` ค่าผลต้องมากกว่า 0 เมื่อ OK
- ชื่อรายการและรอบซ้ำต้องเลือก event ID ให้ชัดเจน คัดเข้ารอบชิงด้วยผู้มีสิทธิ์ ผู้ได้ผลเท่ากันได้อันดับร่วม ไม่สร้างเหรียญจากฮีตอัตโนมัติ
- ผู้ชมที่ไม่มีสิทธิ์เห็นทะเบียนนักกีฬา ยังเห็นผลสาธารณะเป็นโรงเรียน/bib ตาม RLS ได้ เมื่อ bib จับคู่ทะเบียนไม่ได้หรือซ้ำ เว็บไม่เลือกนักกีฬาให้เอง
- หากสร้าง event สำเร็จแต่เขียน result ไม่สำเร็จ อาจมีรายการกรีฑาที่ยังว่างเหลืออยู่ ระบบไม่ลบ event หรือผลอื่นเพื่อแก้ข้อผิดพลาด ให้แก้สิทธิ์แล้วบันทึกซ้ำ
- เหรียญส่ง `gold`/`silver`/`bronze` ลง `medals` ของ competition ที่เลือก กติกา/check constraints และ RLS ในฐานข้อมูลยังเป็นตัวบังคับสุดท้าย
- พิมพ์/PDF ผ่าน browser เลือก Save as PDF ใช้ A4 แนวนอนและฟอนต์ไทยในเครื่อง ไม่ใช่บริการสร้าง PDF บน server

## ตรวจสอบ

```sh
npm test
npm run typecheck
npm run build
npm run test:e2e
```

E2E ใช้ `/usr/bin/chromium` ทดสอบโหมดสาธิตและ hosted API fixture รวมการเขียน normalized payload, school UUID, pagination, revision, กรีฑาฮีต/รอบชิง และการแยก localStorage ไม่มีการส่ง write ทดสอบไปฐานข้อมูลจริง การทดสอบ RLS ใน PGlite ครอบคลุม **legacy schema เท่านั้น** ไม่ใช่หลักฐานยืนยันนโยบาย hosted project ปัจจุบัน

การตรวจ project จริงใช้คำขออ่านอย่างเดียว ไม่แก้ข้อมูลเพื่อทดสอบ ประเด็นที่ยังต้องตรวจด้วยบัญชีจริงคือ constraints/บทบาทที่ไม่ปรากฏใน column metadata, การเขียนตามสิทธิ์, การแก้พร้อมกัน และเวลาที่ session หมดอายุ

# นครโกสัมพีเกมส์ · ปีการศึกษา 2569

Next.js App Router + TypeScript + Tailwind CSS + Supabase หน้าตาขาว–ทอง ฟอนต์ Sarabun และภาพกีฬาใน `public/` รองรับมือถือ คีย์บอร์ด reduced motion และพิมพ์ PDF ผ่านเบราว์เซอร์ โครงสร้าง shadcn อยู่ที่ `components/ui` และ theme/styles อยู่ที่ `app/globals.css`

## เริ่มใช้งานจริง

ใช้ Node.js 24 และ npm 11:

```sh
npm ci
cp .env.example .env.local
# เติมค่าในเครื่องเท่านั้น แล้ว restart server เมื่อเปลี่ยน environment
npm run dev
```

ต้องมี `NEXT_PUBLIC_SUPABASE_URL`, publishable/anon key อย่างใดอย่างหนึ่ง และ `SUPABASE_SERVICE_ROLE_KEY` เฉพาะฝั่งเซิร์ฟเวอร์ ห้ามใช้ `NEXT_PUBLIC_` กับ secret ห้ามนำคีย์หรือ `.env.local` เข้า Git ใช้ environment settings ของ hosting เมื่อนำขึ้นระบบจริง

เว็บโหลด Supabase อัตโนมัติ ไม่มีโหมดสาธิต เมนูสลับบทบาท หรือการเก็บข้อมูลธุรกิจใน localStorage หากเชื่อมต่อไม่สำเร็จจะแสดงข้อผิดพลาดและปุ่มโหลดใหม่ การเปลี่ยนบัญชีจะล้างสิทธิ์และข้อมูลส่วนตัวก่อนตรวจ session ใหม่ Supabase Auth ยังเก็บ session ตามกลไกของ SDK

ผู้ดูแลใช้อีเมล โรงเรียนและกรรมการใช้ username/password สมัครที่ `/school-registration` แล้วรออนุมัติ ผู้สมัครไม่มีสิทธิ์จัดการข้อมูลจนกว่าผู้ดูแลจะอนุมัติ โรงเรียนใหม่ได้รับ `school_admin` กรรมการใหม่ได้รับ `referee` ตาม constraint ของฐานข้อมูลจริง ยังอ่านบัญชีเก่าบทบาท `school`/`recorder` ได้ รายละเอียดอยู่ใน [docs/ACCOUNT-ACCESS.md](docs/ACCOUNT-ACCESS.md)

## Supabase และการบันทึก

ใช้ schema normalized ที่มีอยู่ **ห้ามรัน `supabase/schema.sql` ซ้ำ** เพราะเป็น schema เก่า ไม่ใช่ migration ของรุ่นนี้ การปรับครั้งนี้ไม่แก้ schema, constraint หรือ RLS

| ข้อมูล                              | ที่จัดเก็บ                                                          |
| ----------------------------------- | ------------------------------------------------------------------- |
| โรงเรียน / บัญชี                    | `schools`, `profiles`, Supabase Auth                                |
| รายการ / กติกา / โครงสาย            | `competitions.registration_policy`                                  |
| ทะเบียน / ตำแหน่งตัวจริง–สำรอง      | `registrations.roster_details`                                      |
| ตารางและผลทีม                       | `matches`                                                           |
| รายการและผลกรีฑา                    | `athletics_events`, `athletics_results`                             |
| ประวัติโรงเรียน / โลโก้ / ผู้ฝึกสอน | JSON แบบเก็บประวัติเวอร์ชันใน private Storage `team-files`          |
| คำขอสมัคร                           | `school_registration_requests` และ Auth metadata ที่ backend จัดการ |

Bucket `team-files` ต้องเป็น private รองรับ `application/json` เพิ่มจาก CSV/Excel เดิม ขนาด 2 MB เพียงพอสำหรับข้อมูลที่ API จำกัดไว้ โลโก้ PNG/JPG/WEBP ไม่เกิน 1 MB ส่งผ่าน endpoint ภาพแยก ข้อมูลติดต่อและโทรศัพท์ไม่อยู่ใน public projection

API ตรวจ `getUser()` และ profile จริงก่อนใช้ service key ที่จำกัดงานไว้เฉพาะการอนุมัติ การจัดรายการ การบันทึกผล และข้อมูลโรงเรียนที่มีสิทธิ์ กรรมการบันทึกได้เฉพาะคู่/รายการที่ได้รับมอบหมาย ไม่รับสิทธิ์จากข้อมูลผู้สมัครหรือ role ที่ client ส่งมา ไม่เพิ่มสิทธิ์เขียนตารางผลให้เบราว์เซอร์

- `/api/competitions`: ผู้ดูแลสร้าง/แก้รายการ จัดสาย ตั้งโควตาและโปรแกรม; เลื่อนทีมจากผลที่เซิร์ฟเวอร์อ่านเอง
- `/api/match-results`: บันทึกผล/โปรแกรมเดิม ตรวจ identity, assignment, revision, คะแนนและเวลาซ้ำ
- `/api/athletics-results`: บันทึกผลตามนักกีฬาและรายการจริง ตรวจกรรมการ ผู้เข้าร่วม และชนิดผล
- `/api/schools`: แก้ชื่อเฉพาะโรงเรียนที่มีสิทธิ์ พร้อมตรวจชื่อซ้ำและชื่อเดิมก่อนบันทึก
- `/api/school-profile`, `/api/coaches`: ข้อมูลส่วนตัวเฉพาะโรงเรียนตนเองหรือผู้ดูแล; public projection เฉพาะชื่อย่อ ประเภท และ URL โลโก้

## เตรียมรายการและใช้งาน

1. ผู้ดูแลเข้าสู่ระบบ → **จัดการรายการแข่งขัน** สร้างรายการโดยเลือกกติกา กีฬา เพศ และระดับชั้นตามระเบียบจริง
2. ตั้งสำรองสำหรับแชร์บอล/โยนบอล และโควตากรีฑารายการเดี่ยวตามผู้จัด ระบบไม่เดาจำนวนที่ยังไม่กำหนด
3. เลือกโรงเรียนและจัดสาย ข้อมูลสายบันทึกทันที แต่คู่แข่งขันจะสร้างใน `matches` เมื่อทราบทั้งสองทีมและกำหนดวันเวลา/สนามครบแล้ว ไม่ใช้วันเวลาสมมติ
4. กำหนดกรรมการด้วย UUID ของ profile บทบาท `referee` หรือบัญชีเก่า `recorder`
5. โรงเรียนลงทะเบียนหรือ CSV ในรายการที่ตั้งกติกาแล้ว ระบบตรวจตัวจริง สำรอง จำนวนรวม และโควตารายการกรีฑาตามข้อมูลชุดเดียวกัน
6. กรรมการยืนยันผล ระบบบันทึกสถานะ `finished` ตาม constraint ของฐานข้อมูล และคำนวณคะแนน/เหรียญจากผลที่ยืนยันแล้ว

วันเวลาเป็น Asia/Bangkok และบันทึกเป็น timestamptz UTC ทั้ง `matches` และ `athletics_events` ต้องมีวันเวลาและสนาม รายการเก่าที่ไม่ตรงกติกายังอ่านได้และรักษา identity แต่ไม่รับทะเบียนใหม่จนกว่าผู้ดูแลเตรียมรายการที่ถูกต้อง

ฟุตบอล 7+3, วอลเลย์บอล 6+6, ตะกร้อ 3+2, เปตอง 3+0, วิ่งผลัด 4+4 ใช้เพดานตาม `lib/registration-rules.json` แชร์บอล/โยนบอลรอจำนวนสำรองจากผู้จัด กรีฑาเลือกหลายรายการได้ตามโควตา เปตองไม่มีช่องสำรอง CSV UTF-8 ไม่เกิน 2 MB ใช้ school UUID หรือชื่อจริงที่ไม่ซ้ำ ดาวน์โหลดต้นแบบและรหัสโรงเรียนจากเว็บ

ผลคัดออกที่ยืนยันแล้วแก้คะแนนได้เมื่อผู้ชนะเดิมไม่เปลี่ยน ไม่เปลี่ยนคู่/ผู้ชนะจนทำให้สายถัดไปขัดกัน การจัดสายและสร้างคู่เป็น REST หลายคำขอ หากบางส่วนสะดุดให้โหลดใหม่แล้วใช้ปุ่ม **ตรวจสอบและบันทึกคู่ที่พร้อมแข่งขัน** โดยไม่สร้างสายใหม่หรือทับผลเดิม การตั้งเวลาพร้อมกันในคนละรายการยังไม่มี transaction ครอบคลุมข้ามรายการ ผู้จัดควรตรวจโปรแกรมรวมก่อนเผยแพร่

ข้อมูลประวัติ/ผู้ฝึกสอนใช้ชื่อ successor คงที่ต่อเวอร์ชันและ Storage `upsert:false` เพื่อให้การบันทึกพร้อมกันสำเร็จเพียงหนึ่งคำขอ ที่เหลือได้รับ 409 ให้โหลดใหม่ ห้ามลบไฟล์ประวัติเป็นรายไฟล์เพราะอาจเปิดเวอร์ชันเก่าให้เขียนซ้ำ การแก้ชื่อโรงเรียนและประวัติเป็นคนละคำขอ หากสำเร็จบางส่วนจะแจ้งตรงตามสถานะจริง

## ตรวจสอบและ build

```sh
npm test
npm run typecheck
npm run build -- --webpack
PLAYWRIGHT_TEST_PORT=3100 npm run test:e2e
```

E2E สร้าง production server แยก ใช้ HTTP fixtures และคีย์สมมติ ไม่ส่งข้อมูลไป Supabase จริง ครอบคลุมบัญชี/อนุมัติ สิทธิ์โรงเรียน โควตา CSV การบันทึกและโหลดใหม่ ตาราง ผล เหรียญ PDF มือถือ คีย์บอร์ด และ error/retry ใช้ Chrome บน macOS, `/usr/bin/chromium` หรือ `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`

ผลตรวจระบบจริงและสิ่งที่ปรับอยู่ใน [docs/PRODUCTION-READINESS.md](docs/PRODUCTION-READINESS.md) การทดสอบ RLS ใน PGlite ไม่ใช่หลักฐานแทนนโยบาย hosted project ต้องแยกจากผลทดสอบฐานข้อมูลจริงเสมอ

## เครื่องมือผู้ดูแล

หน้า **โรงเรียน / บัญชี** มีแก้ชื่อ/ตรวจสอบก่อนลบโรงเรียน จัดการ username ย้ายบัญชีโรงเรียน ตั้งรหัสผ่านใหม่ และเริ่มการแข่งขันใหม่พร้อมสำรองข้อมูลเดิม ไม่แสดงรหัสผ่านเดิมและไม่เปลี่ยนบัญชี admin

ปุ่มเริ่มการแข่งขันใหม่ล้างนักกีฬา ผู้ฝึกสอน ตาราง ผล และเหรียญ โดยเก็บโรงเรียน บัญชี และกติกาไว้ ต้องดูจำนวนข้อมูลและพิมพ์ข้อความยืนยันก่อนทำงาน ดูขั้นตอน การดาวน์โหลดสำรอง และการดำเนินการต่อเมื่อสะดุดใน [docs/ADMIN-MAINTENANCE.md](docs/ADMIN-MAINTENANCE.md)
